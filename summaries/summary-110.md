# ECMAScript仕様輪読会：ジェネレーターの`next()`・`yield`と実行コンテキストの切り替え

## 今回のテーマ

今回は、ジェネレーターオブジェクトの`next()`を入口に、停止しているジェネレーターがどのように再開され、`yield`によって呼び出し側へ制御を戻すのかを読み進めました。

中心となったのは、次の抽象操作です。

- `GeneratorResume`：ジェネレーターを再開する。
- `RunSuspendedContext`：停止している実行コンテキストを再開する。
- `Yield`：`yield`式の処理を、ジェネレーターの種類に応じて振り分ける。
- `GeneratorYield`：同期ジェネレーターを停止し、値を外へ渡す。
- `RunCallerContext`：呼び出し側の実行コンテキストへ制御を戻す。

また、仕様を読む途中で、`next()`には引数を渡せること、その引数が停止中の`yield`式の結果になることを実験しました。そこから、ジェネレーターによる双方向の値の受け渡し、対話処理、代数的エフェクトに似た仕組みへと話が広がりました。

## ジェネレーターのメソッドはどこにあるのか

### `.prototype`と、オブジェクト自身のプロトタイプを区別する

本題へ進むために、まず、ジェネレーターオブジェクトから`next()`がどのように見つかるのかを整理しました。

混乱の原因になったのは、次の二つが別のものだという点です。

```js
obj.prototype
Object.getPrototypeOf(obj)
```

`obj.prototype`は、`"prototype"`という名前の通常のプロパティを参照します。一方、`Object.getPrototypeOf(obj)`は、そのオブジェクトがプロパティ探索でたどる、実際のプロトタイプを取得します。

したがって、あるオブジェクトのプロトタイプを知りたいときに、単純に`.prototype`を参照すればよいわけではありません。

今回の関係を確かめるために、次のようなジェネレーター関数を用意しました。

```js
function* g() {}

const i1 = g();
const i2 = g();
```

この場合、`i1`と`i2`の直接のプロトタイプは、どちらも`g.prototype`です。

```js
Object.getPrototypeOf(i1) === g.prototype; // true
Object.getPrototypeOf(i2) === g.prototype; // true
```

さらに、`g.prototype`自身にもプロトタイプがあります。その先にあるのが、ジェネレーターの共通メソッドを持つ組み込みオブジェクトです。

```js
const intrinsicGeneratorPrototype =
  Object.getPrototypeOf(g.prototype);
```

仕様上の`%GeneratorPrototype%`に相当する、この共通オブジェクトを、今回のコードでは`intrinsicGeneratorPrototype`という変数に入れました。

関係を並べると、次のようになります。

```text
i1 / i2
  ↓ プロトタイプ
g.prototype
  ↓ プロトタイプ
%GeneratorPrototype%
  ↓ プロトタイプ
%IteratorPrototype%
  ↓ プロトタイプ
Object.prototype
  ↓
null
```

仕様には`GeneratorFunction.prototype.prototype`という紛らわしい表記も登場します。この表記を、単に「あるジェネレーター関数の`.prototype`」と取り違えないことが、今回の出発点でした。

### 共通のプロトタイプに置いたプロパティを参照する実験

勉強会では、共通のプロトタイプに`a`というプロパティを追加し、二つのジェネレーターオブジェクトから参照しました。

```js
function* g() {}

const intrinsicGeneratorPrototype =
  Object.getPrototypeOf(g.prototype);

intrinsicGeneratorPrototype.a = 1;

const i1 = g();
const i2 = g();

console.log(
  Object.getPrototypeOf(Object.getPrototypeOf(i1)) ===
    intrinsicGeneratorPrototype
);

console.log(
  Object.getPrototypeOf(Object.getPrototypeOf(i2)) ===
    intrinsicGeneratorPrototype
);

console.log(i1.a);
console.log(i2.a);
```

出力は次のとおりです。

```text
true
true
1
1
```

`i1`にも`i2`にも直接`a`を設定していませんが、プロトタイプチェーンをたどることで、共通オブジェクトに追加した値が見つかります。

なお、これは関係を観察するための実験です。組み込みの共通プロトタイプを変更するため、同じ環境のほかのジェネレーターにも影響します。

### `next()`も、この共通オブジェクトから見つかる

`next()`は、この共通のジェネレータープロトタイプにあるメソッドです。

そのため、次の呼び出しでは、

```js
i1.next();
```

`next`というプロパティはプロトタイプチェーンの先から見つかりますが、メソッド内の`this`は`i1`になります。

メソッドの置き場所と、操作されるジェネレーターオブジェクトは別です。

ジェネレーターオブジェクトはイテレーターとして振る舞います。その基本となるのが`next()`なので、まずここを読めば、値を取り出す処理の中心へ進めるだろう、という方針でした。

共通プロトタイプには`return()`や`throw()`もあります。ただし、イテレーターのインターフェースではこれらは必須ではないため、今回はいったん後回しにしました。

## `Symbol.toStringTag`と`[object Generator]`

共通プロトタイプのプロパティを確認する中で、`Symbol.toStringTag`も話題になりました。

ジェネレーターの共通プロトタイプには、タグとして`"Generator"`が設定されています。これがどの操作に使われるのかを確認するため、次のコードを実行しました。

```js
console.log(
  Object.prototype.toString.call(intrinsicGeneratorPrototype)
);

console.log(
  Object.prototype.toString.call(i1)
);

console.log(
  i1.toString()
);
```

結果はいずれも同じでした。

```text
[object Generator]
[object Generator]
[object Generator]
```

### `typeof`の結果を変えるものではない

ここでのタグは、`typeof`のためのものではありません。

主に`Object.prototype.toString`が返す、次の形式の文字列に関係します。

```text
[object タグ名]
```

ジェネレーターオブジェクトでは、継承した`Symbol.toStringTag`によって、タグ名が`Generator`になります。

### `.toString()`でも同じ結果になる理由

途中では、「`Object.prototype.toString.call(...)`ならタグが出るが、普通の`.toString()`では違うのではないか」という確認もありました。

今回のジェネレーターオブジェクトでは、独自の`toString()`に置き換わっていないため、通常の呼び出しでも同じ結果になります。

一方、数値などは独自の`toString()`を持つため、常に両者が同じになるわけではありません。

```js
const number = 123;

number.toString();                       // "123"
Object.prototype.toString.call(number); // "[object Number]"
```

自分で定義したクラスについても、クラス名がそのままタグになるわけではない、という話がありました。独自のタグを使いたければ、`Symbol.toStringTag`で指定できます。

ただし、タグは変更できるため、`[object Generator]`という文字列だけで、その値が本当にジェネレーターとして動作するかを確実に判定することはできません。今回の確認は、表示の仕組みを理解するためのものでした。

## `next()`の本体は`GeneratorResume`へ処理を渡す

`Generator.prototype.next`の仕様そのものは短く、主な仕事を`GeneratorResume`へ委ねていました。

概念的には、次のような処理です。

```text
it.next(value)
  ↓
対象のジェネレーターは it
再開時に渡す値は value
  ↓
GeneratorResumeへ
```

ここで、メソッドを呼び出した対象が`this`として渡されます。

仕様を読み進める前に疑問になったのが、`next()`の引数です。

```js
it.next(value);
```

普段の利用では、`for...of`などがイテレーターを進めてくれるため、`next()`自体を直接書く機会は多くありません。まして、引数を渡す使い方には馴染みが薄い、という反応がありました。

そこで、まず実際に何が起こるのかを調べました。

## `yield`は式であり、再開時に値を受け取れる

### 外へ渡す値と、中で受け取る値がある

今回、大きな確認点になったのは、`yield`が式だということです。

```js
const received = yield 1;
```

この一行には、時間を隔てた二つの動きがあります。

1. `yield 1`で`1`を呼び出し側へ渡し、ジェネレーターを停止する。
2. 後から`next(value)`で再開すると、その`value`が`yield 1`という式の結果になる。

つまり、`yield`の後ろに書いた値と、`yield`式を評価し終えた結果は、別の方向に流れる値です。

```text
ジェネレーター → 呼び出し側
    yield 1 によって 1 を渡す

呼び出し側 → ジェネレーター
    next("返事") によって "返事" を渡す
```

### 最初の実験では、二回目の引数だけが表示された

最初は、`console.log()`の引数に直接`yield`を書いて実験しました。

```js
function* g() {
  console.log("From generator: ", yield 1);
  console.log("From generator: ", yield 2);
}

const it = g();

console.log(it.next("first next call"));
console.log(it.next("second next call"));
```

出力は次のようになりました。

```text
{"value":1,"done":false}
From generator:  second next call
{"value":2,"done":false}
```

ここでは、`"first next call"`は表示されず、`"second next call"`だけが表示されました。

一見すると意外ですが、`console.log()`の呼び出しが、引数の評価を終えるまで実行されないことを考えると整理できます。

```js
console.log("From generator: ", yield 1);
```

この行では、まず`yield 1`を評価しようとします。しかし、その途中でジェネレーターが停止するため、この時点ではまだ`console.log()`は実行されません。

次の`next()`で再開し、`yield 1`の結果が決まってから、ようやく`console.log()`が実行されます。

### 変数へ分けると流れが見えやすい

この動きを確認するため、コードを次のように書き換えました。

```js
function* g() {
  const value1 = yield 1;
  console.log("Passed to next(): 1 ", value1);

  const value2 = yield 2;
  console.log("Passed to next(): 2 ", value2);
}

const it = g();

console.log(it.next("first next call"));
console.log(it.next("second next call"));
console.log(it.next("third next call"));
console.log(it.next("fourth next call"));
```

メモに記録された出力は次のとおりです。

```text
{"value":1,"done":false}
Passed to next(): 1  second next call
{"value":2,"done":false}
Passed to next(): 2  third next call
{"done":true}
{"done":true}
```

順番に追うと、次のようになります。

| 呼び出し | ジェネレーター内で起こること | 呼び出し側へ返る結果 |
|---|---|---|
| 一回目の`next("first next call")` | 関数の先頭から開始し、`yield 1`で停止 | `{ value: 1, done: false }` |
| 二回目の`next("second next call")` | 最初の`yield`の結果が文字列になり、ログを出した後、`yield 2`で停止 | `{ value: 2, done: false }` |
| 三回目の`next("third next call")` | 二つ目の`yield`の結果が文字列になり、ログを出した後、関数末尾へ到達 | `{ value: undefined, done: true }` |
| 四回目の`next("fourth next call")` | すでに完了しているため、本文は実行しない | `{ value: undefined, done: true }` |

### 一回目の`next()`の引数が使われない理由

`next(value)`の引数は、停止していた`yield`式の結果になります。

しかし、一回目の`next()`を呼ぶ時点では、ジェネレーターはまだ本文の実行を始めていません。値を受け取るための、停止中の`yield`式がありません。

そのため、最初の引数は使われません。

```js
const it = g();

it.next("ここに渡しても、受け取るyieldがまだない");
```

一回目の`next()`は、まず最初の停止位置まで処理を進める操作だと考えると理解しやすくなります。

また、停止しているジェネレーターを引数なしで再開した場合、`yield`式の結果は`undefined`になります。

```js
function* g() {
  const value = yield "準備できました";
  console.log(value);
}

const it = g();

it.next(); // 最初のyieldまで進む
it.next(); // undefinedが表示される
```

### 出力で`value`が省略されている理由

メモでは、終了時の結果が次のように表示されています。

```json
{"done":true}
```

ただし、実際の結果オブジェクトは`value: undefined`も持っています。

```js
{
  value: undefined,
  done: true
}
```

JSON形式の表示では、値が`undefined`のプロパティが省略されるためです。この点も、出力を確認する中で触れられました。

## 双方向の受け渡しを何に使うのか

### 値を列挙するだけではないジェネレーター

ここまでの実験から、ジェネレーターは値を順番に返すだけでなく、外側と値を交換しながら処理を進められることが分かりました。

```text
外側：next()で開始する
内側：要求や途中結果をyieldする

外側：要求を処理し、next(応答)で再開する
内側：応答を受け取り、続きを実行する
```

会話では、値を互いに投げ返すような動きとして捉えられていました。

用途としては、途中で入力待ちになるパーサーや、REPLのような対話処理が話題になりました。ただし、パーサーへの適用を考えた際には使いづらかったという経験も共有され、今回その場で決定的な用途が整理されたわけではありません。

### 代数的エフェクトに似た使い方

関連する記事の話から、代数的エフェクトをジェネレーターで表現するアイデアにも話が広がりました。

そこで使われた大まかな説明は、「処理を外側へ渡した後、その場所へ戻ってこられる例外に似ている」というものでした。

通常の`throw`では、例外が外側の`catch`に捕捉されても、投げた場所の直後へ戻って実行を続けることはできません。

```js
try {
  throw new Error("外側へ処理を渡す");
  console.log("ここへ戻って再開するわけではない");
} catch (error) {
  // 例外を処理する
}
```

一方、`yield`なら、外側へ何らかの要求を渡し、その応答を受け取って続きを実行できます。

```js
function* task() {
  const response = yield {
    type: "request",
    message: "必要な値を取得してください"
  };

  return `受け取った値: ${response}`;
}

const it = task();

const request = it.next().value;
// 外側でrequestを解釈して処理する

const result = it.next("取得した値");

console.log(result.value);
// 受け取った値: 取得した値
```

この例のように、内側の処理は「何が必要か」を表し、外側のハンドラーがそれを解釈して、再開に必要な値を返す構成を考えられます。

話の中では、ハンドラーが処理を再開するか、別の形で処理するか、再開せずに終えるかを判断できる点にも触れていました。

ただし、これは理解のための大まかな類比です。JavaScriptのジェネレーターが、そのまま一般的な代数的エフェクトの仕組みを備えているという説明ではありません。会話でも、ジェネレーターでは同じ形の大域脱出ができないことや、説明が概略であることを確認していました。

紹介された記事には非同期ジェネレーターの例もあり、副作用を扱う例として非同期処理と組み合わせているのではないか、という話も出ました。

## クイズボット：入力と出力を交互に扱う例

休憩後には、検索で見つかったクイズボットの例が共有されました。

```js
function* quizBot() {
  const answer1 = yield "最初の元号は？";

  if (answer1 === "大化") {
    const answer2 = yield "正解！では、現在の元号は？";

    if (answer2 === "令和") {
      return "全問正解です！";
    }
  }

  return "不正解です。終了します。";
}

const bot = quizBot();

console.log(bot.next().value);
// 最初の元号は？

console.log(bot.next("大化").value);
// 正解！では、現在の元号は？

console.log(bot.next("令和").value);
// 全問正解です！
```

この例では、`yield`が質問を外へ出す場所になり、次の`next(answer)`が回答を中へ戻す操作になります。

```text
bot.next()
  → 最初の質問を返して停止

bot.next("大化")
  → answer1に回答を入れて再開
  → 正解なら次の質問を返して停止

bot.next("令和")
  → answer2に回答を入れて再開
  → 最終結果を返して終了
```

### 状態を、変数と停止位置で表せる

通常の状態機械として書くなら、たとえば次のような状態を明示的に管理する必要があります。

```text
最初の回答を待っている
二つ目の回答を待っている
終了した
```

ジェネレーターでは、「どの`yield`で止まっているか」と、関数内の変数に保存された値が、その状態を表します。

そのため、質問と回答のやり取りを、通常の関数内の処理の順番として書けます。

会話では「状態機械を自分で書かず、関数のスタックや停止位置に任せられる」という捉え方をしていました。REPLのように、入力を受け取り、処理して出力し、また入力を待つ用途とも対応します。

また、質問を画面へ表示する処理やユーザー入力を取得する処理を、ジェネレーターの外へ置ける点も評価されました。会話中には「純粋な関数だけでできる」という表現がありましたが、厳密には、ジェネレーターオブジェクト自体は`next()`によって状態が変化します。ここでの利点は、対話の筋書きと、実際の入出力処理を分離して記述できることです。

## `GeneratorResume`：再開できるか確認し、実行状態へ移す

動作例を確認した後、仕様の`GeneratorResume`へ戻りました。

これは、対象のジェネレーター、再開時に渡す値、ブランドを表す情報を受け取り、再開処理を行う抽象操作です。

引数の説明には、ECMAScriptの値に加えて、仕様上の`empty`という表記も登場しました。`empty`は、JavaScriptの値である`undefined`とは別の、仕様内部の「値がない」ことを表すものです。

### まず`GeneratorValidate`で対象を検証する

最初に確認したのは、`GeneratorValidate`です。

単に`next()`という名前のメソッドがあるかを見るのではなく、ジェネレーターとして必要な内部スロットを備えているか、ブランドが適切か、といった検証を行います。

また、すでに実行中のジェネレーターを再び再開しようとすると、`TypeError`になります。

```text
停止中のジェネレーター
  → 再開できる

実行中のジェネレーター
  → 同じジェネレーターを重ねて再開することはできない
```

会話では、「すでに再開して実行しているものを、もう一度再開できないようにしている」と理解していました。

### 完了済みなら、終了した結果を返す

ジェネレーターがすでに完了していれば、本文を再び動かさず、次の結果を返します。

```js
{
  value: undefined,
  done: true
}
```

これは、先ほどの実験で、終了後に何度`next()`を呼んでも同じ終了結果になったことに対応します。

### 停止中なら、保存した実行コンテキストを再開する

再開可能な状態として登場したのは、次の二つです。

| 状態 | 意味 |
|---|---|
| `suspended-start` | ジェネレーターは作られたが、本文の実行をまだ始めていない |
| `suspended-yield` | `yield`によって本文の実行を一時停止している |

このどちらかなら、ジェネレーターに保存されている実行コンテキストを取り出し、状態を`executing`へ変更します。

その後、`RunSuspendedContext`へ処理を渡します。

```text
停止中
  ↓ next()
再開可能か検証する
  ↓
保存した実行コンテキストを取り出す
  ↓
状態をexecutingにする
  ↓
実行コンテキストを再開する
```

再開時に渡す値は、正常な再開であることを表すCompletion Recordに包まれて渡されます。

## Completion Recordは、値と制御の種類を表す

仕様を読む中では、`NormalCompletion`や`Abrupt Completion`という用語も確認しました。

Completion Recordは、計算の結果について、単に「どの値か」だけでなく、「どのような制御の結果か」も表す仕様上の記録です。

今回の理解に必要な範囲では、次のように整理できます。

```text
Normal Completion
  通常の処理として得られた結果

Abrupt Completion
  通常の順次実行から外れる結果
  例：throw、returnなど
```

`Abrupt Completion`をどう訳すかについては、「異常終了」「中断」などの表現が話題になりました。

ただし、`return`も含まれるため、常にエラーが起きたという意味ではありません。また、ジェネレーターの「一時停止」と同じ意味で捉えると混乱します。

`RunSuspendedContext`の結果の説明には、ECMAScriptの値のほかに仕様内部の`unused`も登場しました。これも、JavaScriptの`undefined`と同一視するものではありません。

## `RunSuspendedContext`：呼び出し側を止め、対象を動かす

`GeneratorResume`から進んだ先が、`RunSuspendedContext`でした。

この操作は、ジェネレーターだけに使われるものではありません。参照元を確認すると、次のような処理でも使われていました。

- ジェネレーターの通常の再開。
- ジェネレーターの通常以外の再開。
- 非同期ジェネレーターの再開。
- `AsyncBlockStart`。
- `Await`。

停止した処理を再開するための、共通の仕組みとして位置づけられます。

### 実行コンテキストを入れ替える

ジェネレーターを再開する場合、外側の処理が実行されている状態から始まります。

```js
const result = it.next("再開時の値");
```

ここで、`next()`を呼んでいる側の実行コンテキストを一時停止し、ジェネレーターの実行コンテキストを実行コンテキストスタックへ積みます。

すると、ジェネレーター側が現在実行中のコンテキストになります。

```text
再開前
  呼び出し側が実行中
  ジェネレーター側は停止中

再開後
  呼び出し側は停止中
  ジェネレーター側が実行中
```

そして、停止していた計算を再開します。このとき、停止の原因になった操作の結果として、再開用のCompletion Recordを渡します。

ジェネレーターの場合、ここが`next(value)`の値を、停止中の`yield`式へ送り込む仕組みにつながります。

### 再開した後、どうやって戻ってくるのか

`RunSuspendedContext`は、対象を再開した後、その計算から結果が返るのを待ちます。

結果を受け取った時点では、対象のコンテキストはすでにスタックから外され、呼び出し側のコンテキストが再び実行中になっていることが確認されます。

ここで疑問になったのが、その切り替えを誰が行うのか、という点でした。

```text
ジェネレーターを再開するところまでは分かる
  ↓
本文が進む
  ↓
次のyieldに到達する
  ↓
誰がジェネレーターをスタックから外すのか
誰がnext()の呼び出し側へ結果を渡すのか
```

この疑問を解くため、`yield`側の仕様を読むことになりました。

## `Await`や非同期処理との共通性も確認した

参照元を追う途中では、`Await`も`RunSuspendedContext`を使っていることを確認しました。

`await`も、処理を一度停止し、後からその続きを再開するので、ジェネレーターと共通する仕組みがあると理解できます。

実行コンテキストについては、関数やRealmなどの情報を持つことにも触れ、再開のための情報を保持する単位として見ていました。

ただし、今回の会話では、次の点までは十分に整理しませんでした。

- `Await`から再開するとき、どの値がCompletion Recordとして渡されるのか。
- 非同期処理の開始時と、`await`後の再開では何が違うのか。
- `unused`などの仕様内部の値が、どの場面で必要になるのか。

また、`AsyncBlockStart`の呼び出し元を追うと、非同期関数だけでなく、モジュールの実行にも関係していました。これはトップレベル`await`があることと結びつけて理解していました。

今回は同期ジェネレーターを中心に読む方針なので、これらは参照関係の確認にとどめました。

## `yield`式の評価を読む

### 今回確認した三つの形

`yield`式には、大きく次の形がありました。

```js
yield;
```

```js
yield expression;
```

```js
yield* iterable;
```

値を伴う形では、まず後ろの式を評価し、その値を`Yield`へ渡します。

```js
yield 1 + 2;
```

この場合、外へ渡す値は`3`です。

`yield*`は、別のイテラブルへ処理を委譲する形です。仕様がかなり長く、今回知りたかった通常の停止・再開より話が広がるため、詳しくは読みませんでした。

### 普通の関数に`yield`を書けるのか

仕様の断片を見ている途中で、「`yield`は普通の関数にも書けるのではないか」という疑問が出ました。

実際に試すと、通常の関数内で`yield`式を使うコードは構文エラーになりました。

```js
function f() {
  yield 1; // この位置ではyield式を使えない
}
```

したがって、後で出てくる抽象操作の説明だけを見て、「実行時に通常の関数の`yield`も処理するのだろう」と考える必要はありません。構文上の制約も合わせて読む必要があります。

### `yield`や`await`を識別子として使えるか

そこから、`yield`や`await`が、文脈によって識別子として使えるかという話にも広がりました。

特に`yield`については、非strictの通常のスクリプトとstrict modeで扱いが異なることを確認しました。

```js
// 非strictの通常のスクリプトでは許される場合がある
var yield = 1;
```

```js
"use strict";

var yield = 1; // SyntaxError
```

会話では「ソフトキーワード」という表現も使われ、単語だけで常に同じ扱いになるわけではなく、構文上の位置やモードに依存することを話していました。

`await`についても実験や記憶の確認がありましたが、スクリプト・モジュール・非同期関数などの条件を網羅して整理したわけではありません。予約語になった時期についても話題になりましたが、歴史的な経緯の確定までは行いませんでした。

## `Yield`：同期か非同期かで処理を分ける

次に読んだ`Yield`は、外へ渡す値を受け取り、ジェネレーターの種類を調べます。

種類を調べる`GetGeneratorKind`は、次のような区別を返せる操作でした。

```text
同期ジェネレーター
非同期ジェネレーター
ジェネレーターではない
```

### 非同期ジェネレーターの場合

非同期ジェネレーターなら、渡す値に`Await`を適用してから、非同期ジェネレーター用のyield処理へ進みます。

ここで待つ対象は、`yield`で外へ渡そうとしている値です。会話の途中では、`next()`へPromiseを渡した場合との関係も推測されましたが、その点は今回掘り下げませんでした。

### 同期ジェネレーターの場合

同期ジェネレーターでは、外へ返す値をイテレーターの結果オブジェクトにまとめ、`GeneratorYield`へ渡します。

```js
{
  value: 外へ渡す値,
  done: false
}
```

`done: false`なのは、`yield`による停止が、ジェネレーター全体の完了ではないためです。

なお、`GetGeneratorKind`自体が「ジェネレーターではない」という結果も返せることについて、どういう経路で使われるのかという疑問が出ました。ただし、通常の関数では`yield`式を書けないことを確認しており、この操作のすべての利用場面までは追いませんでした。

## `GeneratorYield`：状態を停止中へ変え、呼び出し側へ移る

`GeneratorYield`は、イテレーターの結果オブジェクトを受け取ります。

ここでは、まず現在実行中のジェネレーターの実行コンテキストと、それに対応するジェネレーターオブジェクトを取得します。

その後、ジェネレーターの状態を変更します。

```text
executing
  ↓ yieldに到達
suspended-yield
```

この時点で、ジェネレーターオブジェクト上の状態は「`yield`で停止中」になります。

ただし、状態を書き換えることと、実行コンテキストスタックを切り替えることは別です。ここまででは、まだジェネレーター側のコンテキストで処理しています。

実際に呼び出し側へ制御を戻すのは、続いて呼ばれる`RunCallerContext`です。

## `RunCallerContext`：外側へ戻し、自分は次の再開を待つ

今回の後半で最も難しかったのが、`RunCallerContext`でした。

### ジェネレーターのコンテキストをスタックから外す

まず、現在実行中のジェネレーターのコンテキストを、実行コンテキストスタックから取り除きます。

すると、スタックの一番上には、呼び出し側のコンテキストが現れます。それを再び実行中のコンテキストにします。

```text
yield前のスタック

上：ジェネレーター側
下：呼び出し側
```

```text
yield後のスタック

上：呼び出し側

ジェネレーター側は取り外され、停止している
```

スタックから外れたことは、ジェネレーターの実行状態を破棄したことを意味しません。後から再開できる状態として保持されています。

### イテレーターの結果を呼び出し側へ渡す

次に、呼び出し側を再開します。

その際、`yield`で作ったイテレーターの結果オブジェクトを、正常な結果として渡します。

```js
const result = it.next();
```

呼び出し側では、この`next()`の結果として、たとえば次の値を受け取ります。

```js
{
  value: 1,
  done: false
}
```

これが、ジェネレーターから外へ値が出てくる側の動きです。

### 呼び出し側を再開したところで、ジェネレーター側は停止する

仕様には、呼び出し側へ制御を移すと、この側の処理が一時停止することが説明されていました。

ここで重要なのは、`RunCallerContext`の後続の処理を、そのまま続けて実行するわけではないことです。

```text
ジェネレーター側：
  呼び出し側を再開する
  ↓
  自分はここで停止する

呼び出し側：
  next()の結果を受け取り、処理を続ける
```

ジェネレーター側の続きを進めるには、そのジェネレーターをもう一度再開する必要があります。

また、仕様にあった「再開が二度と起きないかもしれない」という説明について、最初は「二度と起きない」と読んでしまい、途中で訂正しました。

意味するのは、呼び出し側が次の`next()`を呼ばず、そのジェネレーターが停止したままになる可能性もある、ということです。

### 次の`next(value)`で、停止していた処理の続きへ戻る

後から次の呼び出しが行われると、

```js
it.next("応答");
```

停止していたジェネレーター側が再開します。

このとき渡されたCompletion Recordを、`RunCallerContext`の後続処理が受け取り、上位へ返します。それが最終的に`yield`式の結果につながります。

```js
const response = yield "要求";
```

このコードなら、

```text
yield "要求"
  → 外側へ"要求"を渡して停止

next("応答")
  → 停止位置へ戻る
  → yield式の結果が"応答"になる
  → responseへ代入する
```

という流れになります。

## 二つの実行コンテキストが、交互に動く

今回読んだ処理をつなぐと、呼び出し側とジェネレーター側が交互に動きます。

```js
function* g() {
  const answer = yield "質問";
  console.log(answer);
}

const it = g();

const first = it.next();
const second = it.next("回答");
```

流れをまとめると、次のようになります。

```text
呼び出し側                            ジェネレーター側
    │                                       │
    │ it.next()                             │
    ├──────────────────────────────────────>│
    │ 停止                                  │ 本文の実行を開始
    │                                       │ yield "質問"
    │<──────────────────────────────────────┤
    │ { value: "質問", done: false }         │ 停止
    │                                       │
    │ it.next("回答")                       │
    ├──────────────────────────────────────>│
    │ 停止                                  │ yield式の結果が"回答"
    │                                       │ answerへ代入
    │                                       │ console.log(answer)
    │                                       │ 本文が終了
    │<──────────────────────────────────────┤
    │ { value: undefined, done: true }       │ 完了
```

ただし、勉強会の中では、この対応を仕様の各ステップへ完全に結びつけるところで苦戦しました。

特に、次の二つを対応させる必要があります。

- `RunSuspendedContext`が、ジェネレーター側を再開して結果を待つ。
- `RunCallerContext`が、呼び出し側を再開して、自分は次の再開を待つ。

片方から見た「相手を再開して待つ」が、もう片方の実行につながります。通常の関数呼び出しのように、一つの処理が上から下へすぐに完了するものとして読むと、つながりを見失いやすい部分でした。

## 仕様の記述で難しかった点

### 「再開し、値を渡す」という記述の具体性

会話では、実行コンテキストをスタックへ積む・取り除くといった具体的な記述に対し、

```text
コンテキストを再開し、値を渡す
```

という記述の意味がつかみにくい、という指摘がありました。

「どの操作の結果として値を受け取るのか」「停止していたどこへ戻るのか」が、この操作の説明だけでは直感的に見えにくいためです。

そこで、実行コンテキスト自体の説明も確認した方がよいのではないか、という話になりました。

### 抽象操作同士の対応が一か所にまとまっていない

`RunSuspendedContext`には、再開した計算から戻った時点で、対象のコンテキストがスタックから外れていることが示されています。

しかし、その取り外しは、再開された先の`yield`を経由して、`RunCallerContext`で行われます。

```text
next()
  → GeneratorResume
  → RunSuspendedContext
  → ジェネレーター本文
  → Yield
  → GeneratorYield
  → RunCallerContext
  → next()の呼び出し側へ戻る
```

このつながりを把握するには、複数の節を往復して読む必要がありました。

### 停止した抽象操作にも、その後の続きがある

`RunCallerContext`の後半へ進むのは、ジェネレーター全体が最後まで終わるときだけなのか、という疑問も出ました。

ここでは、そのように考えるのではなく、次の再開が起きるたびに、停止していた操作の続きを進める、と読む必要があるという話になりました。

```text
一つ目のyieldで停止
  ↓
次のnext()で、その停止位置の続きへ戻る
  ↓
一つ目のyield式の評価が完了する
  ↓
本文の続きを実行する
  ↓
二つ目のyieldで、改めて停止する
```

「二度と再開されないかもしれない」という注記は、停止したままになる可能性を述べています。ジェネレーターの完了まで、その後続処理を毎回飛ばすという意味ではありません。

## 今回残った課題と次回の予定

今回、コードの振る舞いとしては、次の関係を確認できました。

- `yield`の値は、`next()`の結果オブジェクトを通じて外へ出る。
- 次の`next(value)`の値は、停止していた`yield`式の結果として中へ入る。
- 最初の`next()`には、値を受け取る停止中の`yield`がない。
- ジェネレーターは、状態と実行コンテキストを保持して停止・再開する。
- `yield`時にはジェネレーター側のコンテキストをスタックから外し、呼び出し側へ戻す。

一方、仕様の文章を追って、`RunSuspendedContext`と`RunCallerContext`の停止位置・再開位置・値の受け渡しを完全に対応づけるところは、次回へ持ち越しました。

その整理には、呼び出し側とジェネレーター側の二本の流れを描き、どこで停止し、どこへ値を渡し、どこから再開するのかを図にするとよさそうだ、という話になりました。

次回は、まずこの実行コンテキストの切り替えを納得できる形で整理し、その後、`GeneratorResumeAbrupt`など、ジェネレーターの続きの仕様へ進む予定です。
