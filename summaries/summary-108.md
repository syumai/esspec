# 第108回 ECMAScript仕様輪読会 — 文字列のイテレーターからジェネレーターと実行コンテキストへ

## 1. 今回の出発点：`String.prototype[Symbol.iterator]`

今回読み始めたのは、文字列を順番に列挙するためのメソッド、`String.prototype[Symbol.iterator]` です。

普段は、このメソッドを直接呼び出さなくても、`for...of` を使えば文字列を順番に取り出せます。

```js
for (const c of "abc") {
  console.log(c);
}

// a
// b
// c
```

このとき、文字列からイテレーターを取得するために使われるのが `Symbol.iterator` というキーのメソッドです。直接呼ぶと、次のように操作できます。

```js
const iterator = "abc"[Symbol.iterator]();

console.log(iterator.next());
// { value: "a", done: false }

console.log(iterator.next());
// { value: "b", done: false }

console.log(iterator.next());
// { value: "c", done: false }

console.log(iterator.next());
// { value: undefined, done: true }
```

今回の輪読は、この「文字列を一つずつ取り出す」という身近な処理が、仕様ではどのような仕組みで表現されているかを追うところから始まりました。

ところが、その説明には抽象クロージャー、ジェネレーター、実行コンテキストなどが登場します。そのため、文字列のメソッド一つを読むところから、イテレーターとジェネレーターの基礎を広く確認する回になりました。

## 2. 文字列の列挙単位は「コードポイント」

最初に注目されたのは、文字列のイテレーターが列挙する単位です。

仕様には、文字列の**コードポイントを列挙し、それぞれを文字列として返す**と書かれています。ここで返るのはコードポイントを表す数値ではなく、そのコードポイントに対応する文字列です。[仕様：String.prototype[Symbol.iterator]](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype-%symbol.iterator%)

```js
const iterator = "あ"[Symbol.iterator]();

console.log(iterator.next());
// { value: "あ", done: false }
```

### コードユニット単位の処理との違い

JavaScriptの文字列には、UTF-16のコードユニット単位で扱う操作もあります。たとえば `length` や添字によるアクセスです。

輪読中の実験では、「𩸽」という文字を使って違いを確認しました。

```js
const s = "𩸽";

console.log(s.length);
// 2

console.log(s[0].length);
// 1

console.log(s[1].length);
// 1

console.log([...s]);
// ["𩸽"]
```

「𩸽」はUTF-16では二つのコードユニットで表現されますが、一つのコードポイントです。そのため、文字列のイテレーターでは分割されず、一つの文字列として取り出せます。

この違いを踏まえて、仕様中の位置や長さの扱いを読みました。

- 現在位置は、コードユニット単位で管理する。
- その位置から取り出すものは、一つのコードポイントに相当する部分文字列。
- 正しいサロゲートペアなら、位置を二つ進める。
- それ以外なら、位置を一つ進める。

つまり、内部の位置管理がコードユニット単位でも、外に返す値はコードポイント単位になるように調整しています。

## 3. 呼び出された値を文字列に変換する

`String.prototype[Symbol.iterator]` の説明の冒頭では、まずメソッドの `this` を受け取り、それが利用可能な値かを確認し、文字列に変換する処理を読みました。

ここで登場したのが、次の二つの抽象操作です。

| 抽象操作 | 今回の説明での役割 |
|---|---|
| `RequireObjectCoercible` | `null` や `undefined` を受け付けないようにする |
| `ToString` | 受け取った値を文字列に変換する |

このため、文字列以外の値にメソッドを借りて使うこともできます。

```js
const iterator =
  String.prototype[Symbol.iterator].call(123);

console.log([...iterator]);
// ["1", "2", "3"]
```

一方、`null` や `undefined` では、文字列を列挙する準備の段階で例外になります。

```js
String.prototype[Symbol.iterator].call(null);
// TypeError

String.prototype[Symbol.iterator].call(undefined);
// TypeError
```

ここでの `ToString` は、仕様上の抽象操作の名前です。JavaScriptのコード上にある特定の `.toString()` メソッドを、そのまま一回呼ぶという意味ではありません。

## 4. 抽象クロージャーとは何か

文字列への変換の次に、仕様では **Abstract Closure、抽象クロージャー** を作ります。

今回参加していたメンバーには初めて見る人もいたため、この概念自体の説明に寄り道しました。

### アルゴリズムの一部を、後で実行できるまとまりにする

輪読では、抽象クロージャーを「抽象操作の無名関数版のようなもの」と説明していました。

抽象操作には、通常、次のような名前があります。

```text
ToString
CodePointAt
CreateIteratorResultObject
```

一方、ある処理の中だけで使う手順を、毎回独立した名前付きの抽象操作にする必要はありません。

そこで、手順をひとまとまりにし、別の操作に渡したり、後で実行したりできるものとして表現するのが抽象クロージャーです。

JavaScriptで雰囲気を表すなら、次のような関数に近いものです。

```js
function makeReader(string) {
  return function () {
    // 外側から受け取ったstringを利用できる
    console.log(string);
  };
}

const reader = makeReader("abc");
reader();
// abc
```

ここで内側の関数は、引数がなくても、外側の `string` を利用できます。このように、外側の値を利用できるように保持することを「キャプチャーする」と説明していました。

### JavaScriptから触れる関数オブジェクトとは区別する

ただし、仕様中の抽象クロージャーは、仕様を記述するための概念です。

「実装の内部に、必ずこの形のJavaScript関数オブジェクトが作られる」という意味ではありません。

輪読でも、この点を強調していました。理解のために無名関数と対応させることはできますが、仕様上の処理のまとまりと、JavaScriptプログラムから操作できる値は区別する必要があります。

今回の抽象クロージャーは、先ほど変換した文字列をキャプチャーします。そして、その文字列を順番に読み、値を一つずつ外へ渡す処理を担当します。

## 5. 文字列から一つずつ値を取り出す処理

抽象クロージャーの中身では、文字列の長さと現在位置を使って、先頭から末尾まで進んでいきます。

仕様の手順をそのまま並べる代わりに、処理の意図を文章で整理すると、次のようになります。

まず、現在位置から始まる文字が、コードユニット一つで表されるものなのか、サロゲートペアとして二つ必要なものなのかを調べます。

次に、その結果に応じた長さの部分文字列を取り出し、次に読む位置を更新します。

最後に、取り出した文字列を「まだ列挙の途中である」という情報とともに、呼び出し側へ渡します。

### `CodePointAt` が返す情報

ここで使う `CodePointAt` は、単にコードポイントの数値だけを返す操作ではありません。輪読では、次の情報を持つレコードを返すことを確認しました。

| フィールド | 意味 |
|---|---|
| `[[CodePoint]]` | 読み取ったコードポイント |
| `[[CodeUnitCount]]` | その読み取りで消費するコードユニット数 |
| `[[IsUnpairedSurrogate]]` | 対応相手のないサロゲートかどうか |

今回、次の位置を決めるために使うのは `[[CodeUnitCount]]` です。

```text
コードユニット一つで表されるもの
    → 現在位置を1進める

正しいサロゲートペア
    → 現在位置を2進める
```

コードポイントの数値を改めて文字列に変換するというよりも、元の文字列から、必要な長さの部分をそのまま切り出すところもポイントです。

### 一つずつ渡すことと、処理全体の終了は別

切り出した文字列は、`CreateIteratorResultObject` でイテレーション結果のオブジェクトにし、`GeneratorYield` に渡します。

```js
// 外に渡す値のイメージ
{
  value: "𩸽",
  done: false
}
```

抽象クロージャーの最後には、値を特に持たない正常完了が書かれています。

ここで区別したいのは、次の二つです。

- 列挙の途中では、`GeneratorYield` によって一つずつ値を渡す。
- 全体を読み終えたら、抽象クロージャー自体の処理を終了する。

クロージャーの最後の戻り値だけで、途中の文字をすべて返しているわけではありません。

最後に、このクロージャーを `CreateIteratorFromClosure` に渡し、文字列のイテレーターを作ります。

また、メソッドの `name` プロパティの値が `"[Symbol.iterator]"` になることも読みました。

```js
console.log(String.prototype[Symbol.iterator].name);
// [Symbol.iterator]
```

## 6. イテラブル、イテレーター、イテレーション結果の関係

文字列のイテレーターを理解するために、まずイテレーターのインターフェースを確認することになりました。

ここでは、名前の似た三つのものを区別しました。

| 名前 | 役割 |
|---|---|
| イテラブル | イテレーターを取得できるもの |
| イテレーター | `next()` によって順番に結果を返すもの |
| イテレーション結果 | `next()` が返す、一回分の結果 |

関係をコードの形で表すと、次のようになります。

```js
const iterable = {
  [Symbol.iterator]() {
    return {
      next() {
        return {
          value: /* 今回の値 */,
          done: /* 終わったかどうか */
        };
      }
    };
  }
};
```

### イテラブルには `Symbol.iterator` が必要

イテラブルには、`Symbol.iterator` というキーに、イテレーターを返す関数が必要です。

```js
const obj = {
  [Symbol.iterator]() {
    return /* イテレーター */;
  }
};
```

輪読中に「二重に必要」と表現されていたのは、この構造です。

外側には、イテレーターを取得する入口があります。その入口から返ってくる内側のオブジェクトに、実際に値を進めるための `next()` があります。

### イテレーターには `next()` が必要

イテレーターの中心は `next()` メソッドです。

```js
const iterator = {
  next() {
    return {
      value: 123,
      done: false
    };
  }
};
```

輪読では、追加のメソッドとして `return` と `throw` があることにも触れました。ただし、この二つは今回の手書き実験では扱わず、まず `next()` だけで作ることにしました。

また、一度 `done: true` を返した後は、それ以降の `next()` でも完了状態を返すことが期待される、という説明も読みました。

ただし、手書きのオブジェクトに対して、この振る舞いが自動的に強制されるわけではありません。インターフェースとしての約束と、それを実装するコードの振る舞いは別です。

### `done` と `value` の意味

`next()` が返すオブジェクトには、主に `done` と `value` があります。

```js
// 列挙の途中
{ value: 3, done: false }

// 列挙の終了
{ value: undefined, done: true }
```

`done: false` のとき、`value` は今回取り出した要素です。

一方、`done: true` のとき、`value` はイテレーターの完了時の戻り値として使われます。列挙途中の要素とは役割が異なります。

この違いは、後でジェネレーターの `yield` と `return` を考えると、よりはっきりします。

### プロパティを省略できる

輪読で確認したのは、次の省略です。

```js
// doneを省略すると、完了していないものとして扱われる
{ value: 3 }

// 終了時の値が不要なら、valueを省略できる
{ done: true }
```

補足すると、`value` を省略した場合は、途中でも終了時でも、その値は `undefined` として取得されます。途中の値として `undefined` を返すイテレーターも作れます。

また、`done` は取得した値を真偽値として判定します。省略した場合には `undefined` が得られ、それが偽として扱われます。[仕様：IteratorComplete／IteratorValue](https://tc39.es/ecma262/multipage/abstract-operations.html#sec-iteratorcomplete)

## 7. 手書きで `3 → 2 → 1` を返す

インターフェースを確認した後、実際にイテレーターを書きました。

最初の実験は、カウントを減らしながら `3`、`2`、`1` を返し、その後に終了するものです。

その構造を整理すると、次のようになります。

```js
let count = 3;

const myIterator = {
  next() {
    if (count > 0) {
      return {
        value: count--
      };
    }

    return {
      done: true
    };
  }
};

const obj = {
  [Symbol.iterator]() {
    return myIterator;
  }
};

for (const v of obj) {
  console.log(v);
}

// 3
// 2
// 1
```

作成中には、`Symbol.iterator` の大文字・小文字の誤りや、カウントを減らし忘れる箇所があり、それを直しながら動作を確認しました。

特に、`count` を減らさないままにすると、いつまでも完了に到達しません。イテレーターのインターフェースそのものは簡単でも、どの状態を保持し、どう更新するかは実装側が決める必要があります。

```js
// countを減らし忘れた例
next() {
  if (count > 0) {
    return { value: count };
  }

  return { done: true };
}
```

この例では、`count` が正のままなら、何回呼んでも同じ値を返し続けます。

輪読では、実際に手で書くことで、イテレーターが小さなインターフェースに基づくものであることを確認しました。

## 8. 同じ対象を二回列挙するには

次の課題は、同じ `obj` に対して `for...of` を二回書いたとき、どちらも `3 → 2 → 1` を出すようにすることでした。

```js
for (const v of obj) {
  console.log(v);
}

for (const v of obj) {
  console.log(v);
}

// 期待する結果
// 3
// 2
// 1
// 3
// 2
// 1
```

先ほどのように、同じイテレーターを返し続ける場合、一回目で状態を使い切っています。二回目は、すでに終了した状態から始まります。

そこで、**`Symbol.iterator` が呼ばれるたびに、新しい列挙用の状態を作る**ように変更しました。

輪読では、二通りの書き方を試しました。

### 方法1：状態をオブジェクトのプロパティに持たせる

一つ目は、毎回新しいイテレーターオブジェクトを作り、そのオブジェクトに `count` を持たせる方法です。

```js
const myIterator = () => ({
  count: 3,

  next: function () {
    if (this.count > 0) {
      return {
        value: this.count--
      };
    }

    return {
      done: true
    };
  }
});

const obj = {
  [Symbol.iterator]: function () {
    return myIterator();
  }
};

for (const v of obj) {
  console.log(v);
}

for (const v of obj) {
  console.log(v);
}

// 3
// 2
// 1
// 3
// 2
// 1
```

`myIterator()` を呼ぶたびに、新しいオブジェクトが作られます。それぞれの `count` は `3` から始まるため、列挙の状態が独立します。

作成中には、`next` の書き方を変える必要があるかというやり取りもありました。

この例では、通常の関数として書いた `next` が、呼び出し時の `this` を使ってイテレーター自身の `count` を参照します。

```js
next: function () {
  return {
    value: this.count--
  };
}
```

この使い方なら、`next` をアロー関数にする必要はありません。

### 方法2：状態をクロージャーに持たせる

二つ目は、`Symbol.iterator` の関数内で `count` を宣言する方法です。

```js
const obj = {
  [Symbol.iterator]: function () {
    let count = 3;

    return {
      next: function () {
        if (count > 0) {
          return {
            value: count--
          };
        }

        return {
          done: true
        };
      }
    };
  }
};

for (const v of obj) {
  console.log(v);
}

for (const v of obj) {
  console.log(v);
}

// 3
// 2
// 1
// 3
// 2
// 1
```

こちらでは、`count` はイテレーターオブジェクトのプロパティではありません。返された `next` が、外側のローカル変数を参照します。

`Symbol.iterator` が呼び出されるたびに、新しい `count` が用意されるため、やはり二回の列挙が独立します。

二つの書き方の違いは、列挙の状態をどこに置くかです。

| 書き方 | 状態の置き場所 |
|---|---|
| オブジェクト方式 | 各イテレーターの `count` プロパティ |
| クロージャー方式 | 各 `Symbol.iterator` 呼び出しで作られるローカル変数 |

輪読中には括弧や波括弧の対応を直す場面もありましたが、両方とも同じ出力になることを確認しました。

## 9. 家族の絵文字は一つのまま取り出せるか

手書きのイテレーターを確認した後、文字列の列挙に戻り、次の実験を行いました。

```js
for (const c of "𩸽あいうえお👨‍👩‍👧‍👦") {
  console.log(c);
}
```

メモに残っている出力は、次のようなものです。

```text
𩸽
あ
い
う
え
お
👨
‍
👩
‍
👧
‍
👦
```

「𩸽」は一つのまま取り出せました。一方、「👨‍👩‍👧‍👦」は、見た目では一つの家族の絵文字でも、複数のコードポイントに分かれます。

この絵文字には、人物の絵文字の間に、それらをつなぐ文字が入っています。補足すると、この文字は **ZERO WIDTH JOINER、ZWJ、U+200D** です。

出力がわかりにくいため、見えない部分を名前に置き換えると、次の並びです。

```text
👨
ZWJ
👩
ZWJ
👧
ZWJ
👦
```

輪読では、出力に空行のようなものが見える理由を、この「間に入っている結合用の文字」と結び付けて理解していました。

また、入力中に意図しない置換文字らしきものが入る場面もありました。それを削除し、目的の文字列の列挙を確認しました。

ここで得られた理解は、**コードポイント単位の列挙と、見た目の一文字単位の列挙は一致しないことがある**、というものです。

```js
console.log([..."𩸽"].length);
// 1

console.log([..."👨‍👩‍👧‍👦"].length);
// 7
```

サロゲートペアを正しくまとめてくれることと、複数のコードポイントで作られた絵文字全体をまとめてくれることは、別の話です。

## 10. `CreateIteratorResultObject`：一回分の結果を作る

文字列の列挙処理に登場した補助操作を追うため、次に `CreateIteratorResultObject` を読みました。

これは、値と完了フラグを受け取り、イテレーション結果のオブジェクトを作る操作です。

JavaScriptの表現に対応させると、次のようなものです。

```js
function createResult(value, done) {
  return {
    value,
    done
  };
}

console.log(createResult("a", false));
// { value: "a", done: false }

console.log(createResult(undefined, true));
// { value: undefined, done: true }
```

輪読では、普通のオブジェクトを作り、そこに `"value"` と `"done"` のプロパティを追加するだけであることを確認しました。

### プロトタイプは `Object.prototype`

ここでは `OrdinaryObjectCreate` という抽象操作も登場します。

説明されたのは、渡したプロトタイプを使って新しいオブジェクトを作る、という役割です。

今回の結果オブジェクトでは `Object.prototype` を指定します。`null` をプロトタイプにすることもできる操作ですが、この結果オブジェクトではそうしません。

```js
const result = "a"[Symbol.iterator]().next();

console.log(
  Object.getPrototypeOf(result) === Object.prototype
);
// true
```

つまり、先ほど手書きした `{ value, done }` と同じような、通常のオブジェクトを作る処理だと理解できます。

輪読中には、説明文が「インターフェースに準拠するオブジェクトを返す」「インターフェースに準拠するオブジェクトを作る」と、似た内容を繰り返していることにも軽く触れていました。

## 11. `GeneratorYield` と実行コンテキスト

次に読んだのは `GeneratorYield` です。

こちらは結果オブジェクトを作るだけではありません。ジェネレーターの実行を一時停止し、その結果を呼び出し側へ渡す仕組みに関わります。

説明には、次のような用語がまとまって登場しました。

```text
running execution context
Generator component
GetGeneratorKind
[[GeneratorState]]
suspended-yield
RunCallerContext
```

そのため、まず実行コンテキストを確認することになりました。

### 実行コンテキストは、コードを実行するための情報

実行コンテキストは、現在のコードの実行に必要な情報を管理する、仕様上の概念です。

輪読では、主に次のコンポーネントに触れました。

| コンポーネント | 役割 |
|---|---|
| `Function` | その実行に対応する関数 |
| `Realm` | 組み込みオブジェクトやグローバル環境などに関わる領域 |
| `ScriptOrModule` | 関連するスクリプトまたはモジュール |
| `Generator` | ジェネレーターの実行で用いる、対応するジェネレーター |

「コンポーネント」は、ここでは実行コンテキストを構成する情報の項目を指しています。

また、`ScriptOrModule` は、単なる「現在の実行モードのフラグ」と捉えるよりも、関連するスクリプトやモジュールを示す情報として理解する方が正確です。

### コンテキストは一つだけ存在するわけではない

説明の途中では、実行コンテキストが一つだけ存在し、関数の情報が入れ替わるような表現がありました。しかし、その後に訂正しました。

通常の関数呼び出しでは、関数ごとの実行コンテキストがスタックに積まれます。

```js
function outer() {
  inner();
}

function inner() {
  console.log("inner");
}

outer();
```

イメージは次のようになります。

```text
outer()を呼ぶ前
    呼び出し元のコンテキスト

outer()を実行中
    呼び出し元のコンテキスト
    outerのコンテキスト ← 実行中

inner()を実行中
    呼び出し元のコンテキスト
    outerのコンテキスト
    innerのコンテキスト ← 実行中

inner()から戻る
    呼び出し元のコンテキスト
    outerのコンテキスト ← 実行中
```

同じ実行コンテキストの `Function` を書き換え続ける、という説明ではありません。

また、「常に一つ」というのは、実行コンテキストの総数ではなく、同一のエージェントで、その時点の **running execution context** として実行中になっているものについての話です。停止中のコンテキストはほかにも存在できます。[仕様：Execution Contexts](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-execution-contexts)

### スタックの出入りだけでは説明できない場合

通常の関数呼び出しは、後から積まれたものが先に戻る、LIFOの動きになります。

しかし、輪読では、仕様に「一部の機能では非LIFOの遷移が必要になる」と書かれていることも確認しました。

ここから、Promise、イベントループ、タスクキュー、マイクロタスクなどの話に広がりました。

会話では、Promiseの処理がキューに入り、後で実行されることや、`setTimeout` との違いについて、記憶を持ち寄って説明していました。ただし、この部分は輪読中でも、推測を交えた説明であることを認めていました。

**補足：Promiseを作ることと、後で実行される処理を登録することは区別が必要です。**

`new Promise` に渡した executor は、その場で同期的に実行されます。後から実行される代表例は、`.then()` に登録した反応です。

```js
console.log("A");

const p = new Promise((resolve) => {
  console.log("B");
  resolve();
});

p.then(() => {
  console.log("D");
});

console.log("C");

// A
// B
// C
// D
```

そのため、「Promiseを作ると、その本体がすべて後回しになる」という説明にはなりません。[仕様：Promiseコンストラクター](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-promise-executor)

輪読では、Promiseに関連する処理がマイクロタスク、`setTimeout` が一般にマクロタスクと呼ばれる側であることも確認しました。一方、それらの用語をそのままECMAScript仕様内の用語として読めるわけではなく、ホスト側の実行モデルとの区別が必要だという話もありました。

実行コンテキストのスタックを説明するMDNの図も参照し、後で改めて読み直すとよさそうだという流れになりました。

今回のジェネレーターでは、この非LIFOの話を、さらに具体的に捉えられます。ジェネレーターは、呼び出しから最後まで一気に終わるのではなく、途中の実行状態を保持して停止し、後の `next()` で再開するからです。

### `GeneratorYield` が行うこと

輪読で読んだ範囲を役割として整理すると、`GeneratorYield` は次のことをします。

まず、現在実行しているジェネレーターを、実行コンテキストの `Generator` コンポーネントから取得します。

次に、同期ジェネレーターであることを確認し、状態を `suspended-yield` に変えます。

そして、一回分のイテレーション結果を伴って、呼び出し側の実行へ戻ります。

```text
呼び出し側
    next()を呼ぶ
        ↓
ジェネレーター側
    処理を進める
    値をyieldする
        ↓
呼び出し側
    一回分の結果を受け取る
```

`GetGeneratorKind` については、同期、非同期、ジェネレーターではない場合を区別する操作であることも確認しました。今回扱っている文字列の列挙では、同期ジェネレーターの仕組みを使っています。

## 12. `CreateIteratorFromClosure`：クロージャーからイテレーターを作る

休憩を挟んで、`CreateIteratorFromClosure` を読みました。

名前は「クロージャーからイテレーターを作る」ですが、返すものの説明にはジェネレーターが登場します。

これが、今回の大きな疑問の一つになりました。

### 受け取るもの

この抽象操作は、主に次の情報を受け取ります。

| 引数 | 内容 |
|---|---|
| `closure` | 列挙の処理を行う、引数なしの抽象クロージャー |
| `genBrand` | 種類を区別するための文字列、または `empty` |
| `genProto` | 作るオブジェクトのプロトタイプ |
| `extraSlots` | 必要なら追加する内部スロットの名前のリスト |

クロージャーには、途中で値を渡す処理を含められます。ただし、必ず値を渡す箇所がなければならないわけではなく、何も列挙せずに終わることもできます。

### 内部スロットの「名前のリスト」を作る

まず注目したのは、内部スロットの一覧です。

```text
[[GeneratorState]]
[[GeneratorContext]]
[[GeneratorBrand]]
```

追加のスロットがある場合は、その名前のリストに、上の三つの名前を連結します。

輪読中には、仕様の `« ... »` という記号が何を表すかという話もありました。これはギュメと呼ばれる記号で、ここでは仕様上のリストを囲むために使われています。

また、この段階に並んでいるのは、**スロットの値ではなく、スロットの名前**であることを確認しました。

```text
作成前
    どの名前の内部スロットを用意するかを指定する

オブジェクト作成後
    その内部スロットに値を設定する
```

この名前のリストを `OrdinaryObjectCreate` に渡すことで、指定した内部スロットを持つオブジェクトを作ります。

### ブランドと初期状態を設定する

作成したオブジェクトには、ブランドと初期状態を設定します。

ブランドは、どの種類のジェネレーターかを区別するための情報です。

初期状態は `suspended-start` です。これは、本文の実行をまだ始めていない停止状態を表します。

### ジェネレーター用の実行コンテキストを用意する

次に、新しい実行コンテキストを作ります。

輪読では、呼び出し元のコンテキストを `callerContext`、新しく用意する側を `calleeContext` として区別しました。

新しいコンテキストでは、次のような情報を設定します。

- `Function` は `null`。
- `Realm` は現在のRealm。
- `ScriptOrModule` は呼び出し元から引き継ぐ。

ここでは、ソースコードに書かれた普通の関数オブジェクトを実行するという形ではなく、抽象クロージャーを使うため、`Function` が `null` になります。

その後、呼び出し元を一時停止し、新しいコンテキストをスタックに積みます。そこで `GeneratorStart` を呼び、新しいコンテキストを取り除いて呼び出し元へ戻ります。

輪読中に特に不思議だと感じていたのは、この一時的な切り替えです。

「イテレーターを作るだけなのに、どうして実行コンテキストを一回切り替えるのか」という疑問から、「作成した瞬間に、ジェネレーターの実行が始まるのか」という議論につながりました。

この点は、後で `GeneratorStart` の役割を読むことで整理できます。

## 13. 文字列イテレーターのブランドとプロトタイプ

`String.prototype[Symbol.iterator]` に戻り、`CreateIteratorFromClosure` に何を渡していたかも確認しました。

特に紛らわしかったのが、次の二つです。

```text
"%StringIteratorPrototype%"
%StringIteratorPrototype%
```

見た目は似ていますが、役割が違います。

| 表記 | 今回の役割 |
|---|---|
| `"%StringIteratorPrototype%"` | ブランドとして使う文字列 |
| `%StringIteratorPrototype%` | プロトタイプとして使う組み込みオブジェクト |

文字列の方は `[[GeneratorBrand]]` に入ります。

オブジェクトの方は、作られるイテレーターのプロトタイプになります。

### `next()` はプロトタイプから取得する

作成したイテレーター自身に、`next` メソッドを直接追加しているわけではありません。

`next` は `%StringIteratorPrototype%` にあります。

```js
const iterator = "abc"[Symbol.iterator]();

console.log(
  Object.prototype.hasOwnProperty.call(iterator, "next")
);
// false

console.log(typeof iterator.next);
// function
```

手書きの例ではオブジェクト自身に `next` を書きましたが、組み込みの文字列イテレーターでは、プロトタイプにある共通のメソッドを使います。

その `next()` が内部で呼ぶのが `GeneratorResume` です。輪読では、この接続を見つけたところで、ジェネレーターの再開まで読まないと全体が見えない、という認識になりました。

## 14. ジェネレーターとイテレーターはどう違うか

ここでは一度、「ジェネレーターとイテレーターは同じなのか」という話になりました。

整理すると、イテレーターの方が広い概念です。

イテレーターは、`next()` が一回分の結果を返すというインターフェースを満たすものです。

ジェネレーターは、そのインターフェースを満たす方法の一つです。`yield` による停止と再開を使って、イテレーターとしての振る舞いを実現します。

### ジェネレーター関数と、返されるオブジェクトを区別する

輪読では、`function*` で書いたもの自体と、その呼び出し結果も区別しました。

```js
function* stringGenerator() {
  yield "a";
  yield "b";
  yield "c";
}
```

この `stringGenerator` は、ジェネレーター関数です。

呼び出した結果が、ジェネレーターオブジェクトになります。

```js
const generator = stringGenerator();

console.log(typeof generator.next);
// function

console.log(generator.next());
// { value: "a", done: false }
```

名前が似ていますが、関数と、その関数から作られる列挙用のオブジェクトは別です。

### 手書きのイテレーターが自動変換されるわけではない

参加者からは、「先ほど手で書いたイテレーターも、内部でジェネレーターに変換されて実行されるのか」という質問がありました。

答えは、そうではない、というものでした。

```js
const iterator = {
  next() {
    // 通常の関数として処理を実行する
    return {
      value: 1,
      done: false
    };
  }
};
```

この `next()` は、通常のメソッド呼び出しです。ジェネレーターの `yield` に自動変換されるという説明にはなりません。

一方、ジェネレーターでは、毎回 `next()` の分岐やカウント管理を手書きする代わりに、通常の処理の流れの中へ `yield` を書けます。

```js
function* countdown() {
  for (let count = 3; count > 0; count--) {
    yield count;
  }
}

console.log([...countdown()]);
// [3, 2, 1]
```

輪読では、この形式の方が、状態の管理を細かく意識せずに書ける、一段高い抽象として説明していました。

### Goのイテレーターや、過去の非同期処理との比較

関連する話として、Goのイテレーターについても触れました。

参加者が以前読んだGoの設計文書では、処理の実行を切り替える考え方が印象に残っていたという話があり、JavaScriptのジェネレーターとの類似が話題になりました。

ただし、Goのイテレーターは、呼び出し側へ値を渡すための `yield` 関数を使う形であり、JavaScriptの `next()` ベースのインターフェースとそのまま同じではありません。輪読では、JavaScriptの手書きイテレーターの方が、より直接的に一回ずつの呼び出しを表している、という比較をしていました。

また、`async` / `await` が使えるようになる前に、ジェネレーターで非同期処理を表現していたことや、Babelなどでジェネレーターに関連するランタイムが使われていたことにも触れました。

## 15. ジェネレーターの動作をコードで確かめる

Scrapboxに残っている実験は、次のコードです。

```js
function* stringGenerator() {
  console.log("ここまでGeneratorStart?");
  yield "a";
  yield "b";
  yield "c";
  yield "d";
  yield "e";
}

for (const c of stringGenerator()) {
  console.log("running execution context入れ替わり");
  console.log(c);
}
```

出力は次の順序でした。

```text
ここまでGeneratorStart?
running execution context入れ替わり
a
running execution context入れ替わり
b
running execution context入れ替わり
c
running execution context入れ替わり
d
running execution context入れ替わり
e
```

この実験では、ジェネレーター側が値を渡し、ループの本体がそれを受け取る、という交互の実行を観察しました。

概念的には、次の流れです。

```text
for...of側が次の値を要求する
    ↓
ジェネレーター側が処理を進める
    ↓
yield "a"で停止する
    ↓
for...of側が"a"を受け取り、ループ本体を実行する
    ↓
次の値を要求する
    ↓
ジェネレーター側が続きから再開する
```

### 補足：「最初のログが出た」だけでは実行開始の時点は区別できない

輪読中では、このコードの最初のログまでが `GeneratorStart` に相当するのではないか、という推測がありました。

しかし、**ジェネレーター関数を呼んだ時点では、本文はまだ実行されません。最初の `next()` で本文の実行が始まります。** `GeneratorStart` は、その再開に向けた準備をする操作です。[仕様：GeneratorStart](https://tc39.es/ecma262/multipage/control-abstraction-objects.html#sec-generatorstart)

`for...of` は、イテレーターを取得した後に `next()` を呼ぶため、上の実験だけでは、その二つの時点を見分けにくくなっています。

分けて書くと、違いが明確になります。

```js
function* example() {
  console.log("本文の実行開始");
  yield "a";
}

console.log("作成前");

const generator = example();

console.log("作成後");
console.log("nextを呼ぶ前");

console.log(generator.next());

console.log("nextを呼んだ後");
```

```text
作成前
作成後
nextを呼ぶ前
本文の実行開始
{ value: "a", done: false }
nextを呼んだ後
```

したがって、メモにある `"ここまでGeneratorStart?"` は、輪読中の疑問を表したログです。`GeneratorStart` の処理範囲を確定した名前として読むべきではありません。

## 16. ジェネレーターが持つ三つの内部スロット

後半では、ジェネレーターインスタンスの内部スロット一覧を探しました。

マルチページ版では検索しにくかったため、全文表示へ移動し、一覧を確認しています。

見つかったのは、次の三つです。

| 内部スロット | 管理するもの |
|---|---|
| `[[GeneratorState]]` | 現在の状態 |
| `[[GeneratorContext]]` | このジェネレーターの実行コンテキスト |
| `[[GeneratorBrand]]` | 種類を区別するブランド |

### 状態は四種類

`[[GeneratorState]]` には、次の四種類があります。

| 状態 | 意味 |
|---|---|
| `suspended-start` | 本文をまだ実行していない初期の停止状態 |
| `suspended-yield` | 値を渡した後、続きの実行を待つ停止状態 |
| `executing` | 実行中 |
| `completed` | 完了済み |

輪読では、停止したときに毎回 `suspended-start` に戻るのかという疑問がありました。しかし一覧を見て、開始前の停止と、`yield` 後の停止は別の状態であることを確認しました。

通常の流れを示すと、次のようになります。

```text
suspended-start
    ↓ 最初のnext()
executing
    ↓ yield
suspended-yield
    ↓ 次のnext()
executing
    ↓ yield
suspended-yield
    ↓ さらにnext()
executing
    ↓ 本文が終了
completed
```

一度 `completed` になったジェネレーターは、その本文の実行を再開しません。

## 17. `GeneratorStart` を読む

最後に詳しく追ったのが、`GeneratorStart` です。

名前から実行開始そのものを連想しやすいのですが、この操作では、後で本文を動かすための設定を行います。

### 受け取る本文には二種類ある

`GeneratorStart` は、ジェネレーターと、その本文に相当するものを受け取ります。

本文として使えるのは、次の二種類です。

| 本文の種類 | 対応する例 |
|---|---|
| `FunctionBody` のParse Node | ソースコードに書いた `function*` の本文 |
| 抽象クロージャー | 今回の文字列の列挙処理 |

Parse Nodeについては、構文解析した結果の一部分であり、ここではジェネレーター関数の本文に対応するもの、と説明していました。

```js
function* example() {
  // この本文に対応する構文解析結果
  yield "a";
}
```

文字列イテレーターでは、ソースコード上の本文の代わりに、仕様で作った抽象クロージャーを使います。

### コンテキストとジェネレーターを関連付ける

`GeneratorStart` は、現在実行中のコンテキストを取得し、その `Generator` コンポーネントに、対象のジェネレーターを設定します。

輪読では、「直前に実行コンテキストを作っていたのに、Generatorコンポーネントはまだ設定していなかった」という点を確認しました。

ここでは、似た名前の二つの関係があります。

```text
実行コンテキスト
    Generatorコンポーネント
        → 対応するジェネレーター

ジェネレーター
    [[GeneratorContext]]
        → 対応する実行コンテキスト
```

コンテキスト側からジェネレーターを参照でき、ジェネレーター側からコンテキストも参照できるようにします。

### 本文の実行と終了処理をまとめる

さらに `GeneratorStart` の中では、受け取った本文を実行し、その終了を処理するための、別の抽象クロージャーを作ります。

今回の文字列の例には、二段階のクロージャーがあると考えると整理しやすくなります。

```text
文字列メソッドが作るクロージャー
    文字列を読み、値を一つずつ渡す

GeneratorStartが作るクロージャー
    上の本文を実行し、
    終了や例外を処理する
```

輪読では、内側のクロージャー内に出てくる実行コンテキストは、「そのクロージャーが実際に呼ばれたとき」の実行中コンテキストを取得するものだと確認しました。

クロージャーを作る処理と、クロージャーが後から呼ばれる処理を区別する必要があるため、ここは特に読みにくい箇所でした。

### `Completion(...)` は正常終了に変換する操作ではない

本文の評価結果には、`Completion(...)` という表記がありました。

輪読では最初、正常完了へ変換するものではないかという説明がありましたが、その場で確認して訂正しました。

これは、渡されたものがCompletion Recordであることを確認し、そのまま扱うための操作です。例外による終了を、正常終了に変えるものではありません。

Completion Recordは、実行がどのように終わったかを表す仕様上の情報です。

```text
normal completion
    通常の処理として終了した

return completion
    return文によって終了した

throw completion
    例外によって終了した
```

これらを区別することで、本文を最後まで実行した場合、明示的に `return` した場合、例外が出た場合を別々に処理できます。

### `yield` で停止しただけなら、終了処理には進まない

輪読中に難しかったのは、「本文を評価した結果が返ってくる」という記述と、途中で `yield` することの関係です。

ここは、通常の関数の戻り値だけで考えると混乱します。

ジェネレーターが `yield` したとき、呼び出し側は一回分の結果を受け取れます。しかし、ジェネレーター本文そのものは、その場所で終了していません。

```js
function* example() {
  yield "a";

  console.log("まだ本文の続きがある");

  yield "b";
}
```

最初の `next()` では `"a"` を受け取れますが、本文には続きが残っています。

本文の実行全体が終了して初めて、`GeneratorStart` が準備した終了処理へ進みます。

### 完了時には `done: true` の結果を作る

本文の終了後には、状態を `completed` にします。

正常に末尾へ到達した場合、完了時の値は `undefined` です。

明示的に `return` した場合は、その値を完了時の値として使います。

```js
function* example() {
  yield "a";
  return "終了時の値";
}

const generator = example();

console.log(generator.next());
// { value: "a", done: false }

console.log(generator.next());
// { value: "終了時の値", done: true }

console.log(generator.next());
// { value: undefined, done: true }
```

これが、前半で読んだ「`done: true` のとき、`value` はイテレーターの戻り値になる」という話につながります。

`for...of` では、その完了時の値を、ループ本体の要素としては取り出しません。

```js
for (const value of example()) {
  console.log(value);
}

// a
```

例外で終了した場合は、完了結果オブジェクトに包んで正常な値として返すのではなく、例外として呼び出し側へ伝わります。

```js
function* example() {
  yield "a";
  throw new Error("失敗");
}

const generator = example();

console.log(generator.next());
// { value: "a", done: false }

generator.next();
// Error: 失敗
```

### 「このステップには到達しない」というAssert

終了処理の後には、呼び出し側のコンテキストを再開する記述があり、そのさらに後に「このステップには決して到達しない」というAssertがありました。

輪読では、こうしたAssertを初めて見たという反応がありました。

これは、呼び出し側へ制御を渡した後、この場所の処理が通常の関数呼び出しのようにそのまま続くことはない、という仕様上の確認です。

また、Assertは、JavaScriptプログラム中の例外処理と同じものではありません。仕様を読むときの前提や、成立するはずの条件を表しています。

### 最後の設定が、今回もっとも難しかった

`GeneratorStart` の最後では、実行コンテキストのコード評価状態を設定し、そのコンテキストが再開されたときに、用意したクロージャーが引数なしで呼ばれるようにします。

輪読では、この英文の主語や目的語を追うこと自体に苦労していました。

意味を整理すると、次のようになります。

```text
今この場で本文を実行する
```

ではなく、

```text
後でこのコンテキストが再開されたら、
用意した処理を実行するように設定する
```

ということです。

この設定をしたコンテキストを `[[GeneratorContext]]` に保存して、準備を終えます。

これにより、`CreateIteratorFromClosure` で一時的にコンテキストを切り替える理由も見えてきます。ジェネレーター用のコンテキストを実行中のものとして扱い、そこに再開時の処理を設定するためです。

本文を最初の `yield` まで実行するための切り替えではありません。

## 18. 今回たどった仕組みのつながり

今回読んだ要素を、文字列の列挙に結び付けると、次のようになります。

```text
"𩸽abc"[Symbol.iterator]()
    │
    ├─ 対象を文字列として用意する
    │
    ├─ 一つずつ文字を取り出す抽象クロージャーを作る
    │
    └─ CreateIteratorFromClosure
          ├─ ジェネレーター用の状態を持つオブジェクトを作る
          ├─ 文字列イテレーターのプロトタイプを設定する
          ├─ 専用の実行コンテキストを作る
          └─ GeneratorStartで再開の準備をする

iterator.next()
    │
    └─ プロトタイプのnext()
          └─ GeneratorResume
                └─ 保存した実行コンテキストで処理を進める
                      ├─ 次のコードポイント分を切り出す
                      ├─ 一回分の結果オブジェクトを作る
                      └─ GeneratorYieldで呼び出し側へ渡す
```

輪読では、`GeneratorResume` の詳しい中身までは読み切っていません。上の図の再開部分は、各操作の接続を理解するための補足です。

当日の到達点は、文字列の列挙が、単に添字を増やすだけの説明ではなく、停止と再開のできるジェネレーターの仕組みを利用して記述されている、と確認したところでした。

## 19. 次回はジェネレーターを先取りして読む

終盤では、ここで読むのをやめると、作ったジェネレーターがその後どう使われるかが見えないままになる、という話になりました。

そこで、文字列メソッドの続きを読む前に、ジェネレーターオブジェクトの章を先取りして読む方針にしました。

```text

    ↓
```
